# Company Admin email password recovery

## Scope and identity

The Angular 22 Company Admin login now links to `/forgot-password`. The existing login route and JWT payload/validation are unchanged. Recovery requires the existing globally unique `users.login_id` plus registered `companies.email` (case-insensitive email comparison). Company emails are not unique; no company ID from the browser is trusted. Only active `company_admin` users belonging to active companies qualify. Staff `company_user` accounts have no personal email; their existing admin-managed password change remains available. Super Admin and Customer recovery remain separate.

## API and state

POST `/auth/company/forgot-password`: `{login_id,email}`; always generic for eligible, unknown, ineligible, account-throttled and SMTP failure requests. POST `/auth/company/verify-reset-otp`: `{login_id,email,otp}` returns an opaque 5-minute reset token. POST `/auth/company/reset-password`: `{reset_token,new_password}` consumes authorization and returns a success message without creating a session.

OTP: six cryptographically random digits, five-minute expiry, five failed attempts, 60-second resend cooldown, previous OTP/token invalidated on resend. HMAC-SHA256 storage is domain-separated using existing SECRET_KEY; reset tokens contain 256 random bits and only their HMAC is stored. Row locks and conditional updates enforce single consumption; password hash fingerprint invalidates recovery if another password change occurs. User and company eligibility is checked again. Recovery state and rate counters persist in MySQL across workers/restarts. Limits: five issue requests per login ID per hour, 60 recovery endpoint requests per source per hour. Counters include unknown accounts; source-limit 429 responses do not disclose account eligibility. Do not enable SQL parameter logging in production.

SMTP delivery executes immediately, without the welcome worker, using the existing encrypted multipart SMTP transport. The OTP is usable only after provider acceptance; delivery failure invalidates prior credentials and logs only an exception class and operational guidance. No tests send real mail. SMTP acceptance is not proof of inbox receipt. Synchronous SMTP can introduce response timing differences; edge abuse controls remain necessary. Rate rows contain HMAC identifiers rather than raw email or source addresses. Schedule bounded cleanup of rate rows whose window_start is older than your retention policy (for example 48 hours); do not delete active windows.

Passwords use existing bcrypt and existing policy: at least 8 characters, maximum 72 UTF-8 bytes. Only the selected user's password hash changes. Existing JWT architecture has no company session-version enforcement or refresh-token registry. Existing access tokens therefore remain valid until their configured expiry; this change does not claim universal session revocation. Changing that policy requires a separately reviewed authentication change. No browser localStorage recovery credentials are written.

## Controlled deployment

No new environment variables. Reuse SECRET_KEY consistently across Cloud Run instances, and SMTP_HOST, SMTP_PORT (587 by default), SMTP_USERNAME, SMTP_PASSWORD, SMTP_FROM, SMTP_USE_TLS=true and SMTP_USE_SSL=false. Port 465 requires SMTP_USE_SSL=true and SMTP_USE_TLS=false. Exactly one encrypted transport is required. Bind credentials from Google Secret Manager; do not put values in source or deployment logs. Check outbound connectivity, sender authorization and provider quotas. Request timeout must allow the SMTP transport's 30-second timeout. Use HTTPS and trusted ingress. Source identity uses request.client.host; do not trust arbitrary forwarded headers. Confirm Cloud Run/ASGI trusted-proxy configuration supplies the real source; a shared proxy address may throttle legitimate users together.

## Rollback

Roll back frontend and backend code together; leave additive recovery tables in place to preserve evidence and avoid disrupting existing tables. Recovery authorizations must not be reused when re-enabling: invalidate outstanding recovery OTP/token columns in a reviewed, recovery-table-only maintenance operation. Do not restore old user passwords or rotate shared secrets as a routine rollback. If explicitly authorized to remove the feature tables, the migration downgrade removes only the two new tables; never downgrade earlier migrations accidentally. No deployment, push, production migration or production data operation was performed.
